# worldchain-exex

A [reth](https://github.com/paradigmxyz/reth) Execution Extension (ExEx) for the OP-Stack Worldchain node.
It runs inside the `op-reth` process, and streams each committed block (header, transactions, call traces, logs)
over gRPC on a unix socket (`/var/run/worldchain/node_stream.sock`, see `proto/nodestream.proto`) to `tank-engine`.

## Build status — read this first

**Verified: the crate builds from this repository against public upstream reth.** From a fresh clone of this repository
(commit recorded in the PR description), `cargo build --release --locked` in `exex/` completed successfully on 2026-10-27
(Debian 13, rustc/cargo 1.99.1, 8 CPU, empty `target/`, empty `CARGO_HOME`, ~4 minutes). It produced the `worldchain-exex`
and `reset_checkpoint` binaries. **That is a compile check only.** It does not show that the ExEx runs, that it streams
correctly, or that the result is identical to the binary that runs in production; no end-to-end test was run.

* `Cargo.toml` pins upstream reth at `27a8c0f5a6dfb27dea84c5751776ecabdd069646` (the public `v1.9.3` release commit, 2025-11-18).
  The ExEx sources compile against that unmodified upstream commit; no `[patch]` section is needed.
* **Difference from production (unchanged):** production builds this crate against a *locally modified* checkout of reth at the
  same upstream commit (its directory name refers to a "cifs-stall" workaround). Those modifications are **not included** in this
  repository. The public build therefore uses unmodified upstream reth and may behave differently at runtime from the production
  binary (what the modifications change is not documented here). Only compilation was verified here.
* `Cargo.lock` is committed and was generated by cargo from the public dependency definitions in `Cargo.toml` (no production
  lockfile was used). Always build with `--locked`. Without it, cargo resolves the newest compatible versions and the build fails:
  a fresh resolution picks `alloy-sol-macro` / `alloy-sol-type-parser` / `syn-solidity` 1.7.3 next to the pinned `alloy-sol-types`
  1.4.1 (failing in `alloy-dyn-abi` and `alloy-provider 1.0.41`: missing `abi_decode_*_with_config` / `AbiDecoderConfig`), and
  `alloy-rpc-client` / `alloy-transport*` / `alloy-json-rpc` 1.8.3 next to `alloy-provider` 1.0.41. The committed lock was aligned with
  targeted `cargo update -p <crate> --precise <version>` steps: the alloy-core sol-macro family to 1.4.1 and the alloy
  transport/rpc family to 1.0.41. The lock was not edited by hand.
* Prerequisites on a clean Debian 13 host (verified here with equivalents of these on a box without root, see note):
  a Rust toolchain >= 1.88 (reth's `rust-version`; 1.99.1 used), `git`, a C compiler (`gcc`), GNU `make`
  (`tikv-jemalloc-sys`), `libclang` (`reth-mdbx-sys` uses bindgen; Debian package `libclang-dev`, or set `LIBCLANG_PATH`),
  and `protoc` (`protobuf-compiler`, used by `tonic-build`). OpenSSL and `pkg-config` are **not** needed for the ExEx (its dependency graph
  contains no `openssl-sys`); they are needed for `tank-engine`.
  Note: on the verification box those tools were supplied without root (a pip `libclang` 18.1.1 wheel with
  `BINDGEN_EXTRA_CLANG_ARGS` pointing at the gcc/libc include directories, GNU make 4.4.1, protoc 25.3) rather than installed with `apt`;
  the Debian package names above are the expected equivalents and were not installed or tested by `apt` there.
* `EXEX_BYPASS_UNDER_BLOCK` (env, default `0`): block-number threshold read at startup and logged with the ExEx head; see `src/main.rs`.
